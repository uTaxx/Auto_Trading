# Auto_Trading 시스템 설명서

작성일 2026-09-22. 코드(이 저장소의 `main` 브랜치, 커밋 `3b05f65` 기준)를
직접 열어서 확인하고 썼다. 확인하지 못한 부분은 "확인하지 못했다"고
적었다.

## 결론

지금 있는 것은 **과거 시세로 적립식 매수 기법을 시험해 보는 백테스트
시뮬레이터**다. 실제 증권사에 주문을 내는 코드는 이 저장소 어디에도
없다. 시세 수집부터 전략 계산, 결과 저장, 화면 조회까지 전부 사람이
버튼을 눌러야 시작되는 수동 과정이고, 자동으로 매일 도는 것은 하나도
없다. "적립식 매수 기법을 실제 트레이딩까지 연결하는 구조"는 지금은
설계도가 아니라 의도이고, 그 사이를 메우려면 최소 세 가지(환율 계산,
비용 반영, 증권사 연결)가 새로 필요하다. 아래에 하나씩 적는다.

## 1. 무엇을 위해 만들었나

과거 시세를 놓고 "이런 방식으로 꾸준히 샀다면 어떻게 됐을까"를
계산해 보는 도구다. 매수 방식(전략)을 여러 개 만들어서 성적을 견주고,
변수 조합을 자동으로 시험해서 그중 나은 조합을 찾는다. 목표는 이렇게
찾은 조합을 실제 계좌의 매매로 이어 가는 것이다. 지금은 그 앞 단계,
즉 "무엇을 살지 시험하는" 부분만 만들어져 있다.

## 2. 지금 있는 것

### 2-1. 시세 수집

`scripts/update_prices.py`가 야후 파이낸스에서 일봉(시가·고가·저가·
종가·거래량)을 받아 구글 드라이브(`01_시세원본/<종목>/daily.csv`)에
쌓는다. 종목은 사람이 직접 티커를 입력한다(예: SPY, QQQ). 이미 받아 둔
것이 있으면 마지막 날짜 다음부터만 받아 이어 붙이고, 처음부터 다시
받을 수도 있다. 미국 달러/원화 환율(KRW=X)도 같은 방식으로 받는데,
**이 환율은 대시보드에서 종가를 원화로 환산해 보여주는 차트에만 쓰이고,
아래 2-2의 실제 손익 계산에는 전혀 쓰이지 않는다.** 이 둘의 불일치가
3-1의 첫째 항목이다.

### 2-2. 백테스트 엔진(`src/auto_trading/backtest.py`)

매수 방식 네 가지를 지원한다.

- **일회 매수**: 첫날 전체 금액으로 한 번에 산다.
- **적립식 매수**: 정해진 금액을 정해진 간격(거래일 단위)마다 산다.
- **적립식 매수 + 이동평균선 조건**: 이동평균선 아래일 때와 위일 때
  매수 금액·빈도를 각각 다르게 둘 수 있다(한쪽만 둘 수도 있다).
- **등락률 기준 비중 조절 매수**: 최근 평균가 대비 등락률 구간마다
  매수 금액을 다르게 둔다.

네 방식 모두 익절선·손절선을 선택으로 걸 수 있다(매수평균가 대비
비율, 둘 중 하나라도 닿으면 전량 매도). 하루 단위로 계산하며, 그날의
매도(익절·손절) 판단을 먼저 하고 그다음에 매수 판단을 한다. 결과로
날짜별 현금·보유수량·평균단가·평가금액·실현손익·평가손익·총자산을
전부 남긴다.

### 2-3. 최적 조건 찾기(`src/auto_trading/optimize.py`)

위 네 방식의 변수 후보를 여러 개 한꺼번에 넣으면(예: 매수 금액 후보
3개 × 매수빈도 후보 3개) 조합을 전부 계산해서 수익률 내림차순으로
보여준다. 조합 수는 200개로 막아 둔다. 1등만 보여 주지 않고 계산한
조합 전부를 남기고, 최대낙폭도 같이 보여 준다(수익률만 보고 고르지
않게 하려는 것이다).

### 2-4. 결과 저장과 조회

계산 결과는 구글 드라이브에 JSON(대시보드가 읽는 원본)과 서식 있는
엑셀 두 가지로 남는다. 엑셀은 종목·전략 조합마다 하나씩 만들어지고
그 안에 일별 매매 기록(그날 매수·매도 금액, 매도 유형, 누적수익률)이
다 들어 있다. 대시보드의 비교 결과 화면에서 표·그래프로 보거나, 엑셀을
그대로 열어 보거나, 결과와 그 원본 엑셀을 한꺼번에 지울 수 있다.

### 2-5. 대시보드(`dashboard/`)

정적 HTML/JS로 만든 화면이고 GitHub Pages로 나간다. 화면의 모든 동작은
n8n 웹훅 하나(`AutoTrading_시세업데이트` 워크플로, 경로 10개)를 거쳐
GitHub Actions를 실행시키는 방식이다. 시세 수집, 전략 비교, 최적 조건
찾기 셋 다 "버튼을 누르면 GitHub Actions가 돌고, 끝나면 화면이 자동으로
확인해서 알려주는" 같은 구조를 쓴다.

### 2-6. 전부 수동이다

`.github/workflows/`의 네 워크플로(시세 수집, 전략 비교, 최적 조건
찾기, 대시보드 배포) 전부 `workflow_dispatch`로만 실행된다.
**정해진 시각에 저절로 도는 것(`schedule` 트리거)이 하나도 없다.**
매일 아침 시세를 받거나 밤에 최적 조건을 다시 계산하는 자동 실행은
지금 없다.

## 3. 백테스트 계산이 깔고 있는 가정

수익률(%)과 최대낙폭(%) 자체는 아래 가정과 무관하게 상대값이라 계속
쓸 수 있지만, 절대 금액(총투자금·실현손익·평가손익·합계, 전부 "원"으로
표시됨)과 실제 매매로 넘어갈 때는 아래를 하나씩 봐야 한다.

- **환율이 반영되지 않는다.** "총자본(원)"에 사람이 입력한 숫자를,
  야후에서 받은 원종목 통화(미국 ETF면 달러) 종가로 그대로 나눠서
  주식 수를 계산한다(`backtest.py`의 `bought_shares = buy_amount /
  close`). 즉 "총자본 1,000만 원"을 입력해도 실제로는 "1,000만 달러"인
  것처럼 계산한다. 화면에 뜨는 "원" 단위 절대 금액(총투자금·실현손익
  등)은 이 때문에 실제 원화 금액이 아니다. 수익률(%)은 같은 통화
  단위를 시종일관 쓰기 때문에 이 문제와 무관하게 맞다. 원화 계좌로
  실제 매매하려면 매수 시점 환율로 원화→달러 환전을 계산에 넣어야
  한다.
- **수수료·세금·슬리피지가 없다.** 매수·매도 어디에도 거래 비용을
  빼지 않는다. 미국 주식은 매매수수료 외에 양도소득세(분리과세)까지
  실제 손익에 영향을 준다.
- **체결가가 그날 종가다.** 매수·매도(익절·손절) 판단과 체결이 같은
  날 같은 종가에서 일어난다. 실제 주문은 다음 날 시가에 체결되거나
  (그 사이 갭이 생긴다), 지정가·시장가에 따라 체결가가 달라진다.
- **정수 단위로 사지 않는다.** 소수 단위 매수를 허용한다(코드 자체가
  "단순화한 것"이라고 적어 둔 부분이다). 실제 국내 증권사는 대부분
  정수 주 단위로만 체결된다(미국 주식은 소수 매매를 지원하는 증권사도
  있다).
- **결제일(T+2)이 반영되지 않는다.** 매도한 금액을 그날 바로 다시
  살 수 있다고 계산한다. 실제로는 매도 대금이 보통 2거래일 뒤에
  들어온다.
- **부분 매도가 없다.** 익절·손절은 항상 전량 매도다. 분할 익절 같은
  전략은 지금 표현할 수 없다.
- **생존 편향은 크지 않다.** 종목을 사람이 직접 골라 입력하므로(예:
  SPY, QQQ), 상장폐지되거나 나중에 편입된 종목을 자동으로 골라
  넣는 구조가 아니다. 다만 사람이 "지금 아는 종목"만 고르는 것
  자체가 이미 사후 편향이라는 점은 남는다.

## 4. 실제 매매까지 남은 거리

지금 구조와 실제 매매 연결 사이에 최소한 이래 있어야 하는 것들이다.
우선순위는 매기지 않았다(어느 것부터 할지는 판단이 필요한 부분이다).

1. **환율 계산을 실제 계산에 넣는다.** 지금은 차트 표시용으로만 쓰는
   환율(KRW=X)을 `run_backtest`의 매수 수량 계산에도 쓰게 고친다.
2. **비용 모델(수수료·세금·슬리피지)을 추가한다.** 0으로 둔 지금
   가정을 걷어내고, 실제 증권사 수수료율과 미국 주식 양도소득세를
   반영한다.
3. **체결 시점을 현실화한다.** 신호가 난 날의 종가가 아니라 다음
   거래일 시가(또는 그날 실제 주문을 넣을 수 있는 시점의 가격)로
   체결을 계산해서, 신호와 체결 사이의 시차·갭을 반영한다.
4. **정수 주 단위 체결을 반영한다**(증권사·상품에 따라 다르다).
5. **증권사 API 연결이 있어야 한다.** 지금 저장소에는 어떤 증권사
   API 코드도 없다. 계좌 조회, 주문 실행, 체결 확인, 잔고 대사가
   전부 새로 필요하다.
6. **사람의 승인 절차가 있어야 한다.** 지금은 "계산 결과를 보고
   사람이 판단"하는 데서 끝난다. 실제 주문으로 이어지려면 그 판단을
   승인으로 바꾸는 절차(무엇을, 언제, 얼마나 살지 확정하는 단계)가
   있어야 한다.
7. **리스크 관리가 있어야 한다.** 백테스트의 익절·손절은 계산 결과일
   뿐이다. 실제 계좌에서는 장중에 가격을 감시하고 실제로 주문을
   내는 절차, 그리고 그 절차가 실패했을 때(주문 거절, API 오류,
   네트워크 단절)의 대응이 있어야 한다.
8. **자동 실행 일정이 있어야 한다.** 지금은 전부 수동이다. 실거래로
   가려면 최소한 "언제 시세를 받고 언제 신호를 내는지"가 정해진
   일정으로 저절로 돌아야 한다.
9. **매매 기록과 실제 계좌를 맞춰 보는 절차가 있어야 한다.** 지금
   결과는 전부 "계산해 본 것"이다. 실거래가 시작되면 계산과 실제
   체결이 다를 수 있고(위의 체결가·비용 가정 때문에), 그 차이를
   확인하는 절차가 필요하다.

**참고할 수 있는 선례가 있다.** 이 계정의 다른 저장소(`muwon406`,
국내 단기 매매 시스템)가 위 7~9번에 해당하는 구조(장중 손절 감시,
사람 승인 절차, 실거래·백테스트 결과를 같은 화면에서 구분해서 보여
주는 것 등)를 이미 실제로 운영하고 있다. 다만 그 저장소는 계좌·인증
키·자동 실행을 이 저장소(`auto_trading`)와 완전히 분리해서 쓰고
있고, 이 저장소의 코드가 그 구조를 가져다 쓰고 있지는 않다. 구조를
참고할 수 있다는 뜻이지, 지금 연결돼 있다는 뜻이 아니다.

## 5. 확인하지 못한 것

- 실제 증권사 계좌(국내든 해외든)를 이 프로젝트 명의로 준비했는지는
  확인하지 못했다. 이 저장소 안에는 그런 설정이 없다.
- 원화→달러 환전을 어느 시점 환율로, 어떤 수수료로 계산할지에 대한
  결정은 아직 없다(사람이 정할 부분이다).
